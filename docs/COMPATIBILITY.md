# Byte compatibility: what is accepted, rejected and untested

Generated by `scripts/run-reverse-differential.sh --markdown`. Do not edit by
hand.

Two directions, and they are not symmetric:

- **reverse** (C SQLite writes, SQLeanite reads) is the direction with no prior
  art and is measured by the matrix below, one live cell per feature;
- **forward** (SQLeanite writes, C SQLite reads) is checked by
  `scripts/run-forward-compat.sh`: for every workload shape C runs
  `PRAGMA integrity_check` *and* must read the same schema and the same rows it
  reads from its own file. Ten of eleven shapes are clean on every check; the
  eleventh has one bounded, transient exception, stated in full below rather than
  averaged away.

## Write-side page size: a stated asymmetry, not a gap being closed

`PhysicalCodec.pageSize = 4096` is threaded through sixteen modules and baked
into type signatures such as `Storage.Page pageSize`. Parameterizing it is
surface-widening in effect, so the decision is to state the asymmetry:

> **SQLeanite reads 1024, 4096, 8192 and 65536 byte pages, and writes 4096 only.**

A file written by SQLeanite is therefore always a 4096-byte-page SQLite file,
which C SQLite reads unconditionally; nothing is lost on the forward direction.

## Value rendering differs from the `sqlite3` shell, and is not a storage claim

Two differences are known, both in `Main.lean`'s unverified result rendering
rather than in storage or comparison:

| value | `sqlite3` prints | `sqleanite` prints |
|---|---|---|
| REAL with an integral value, e.g. `3.0` | `3.0` | `3` |
| BLOB, e.g. `x'00ff10'` | the raw bytes | `X'00FF10'` |

Both files round-trip correctly: the matrix cells for REAL and BLOB below read
those values through *ordering and predicates* rather than through rendering, so
they test the codec and the comparison, which are the parts with theorems.
Rendering lives in the executable TCB (see `docs/TRUST.md`) and is deliberately
not claimed to match the shell byte for byte.

## Reverse-direction matrix

Every cell is a C-written file read by both engines with identical queries.
`accepted` means SQLeanite's output equalled C's exactly. `declared` means the
file is outside the supported subset and SQLeanite refused it with an ordinary
diagnostic and a nonzero exit -- checked, not assumed, and a cell that starts
succeeding fails this script so the declaration cannot go stale.

| feature | page size | result | note |
|---|---:|---|---|
| plain-table | 4096 | accepted | Single-page table, INTEGER PRIMARY KEY |
| multipage-interior | 4096 | accepted | Multi-level interior nodes (2,000 rows x 800B) |
| secondary-index | 4096 | accepted | Secondary index B-tree traversal |
| text-primary-key | 4096 | accepted | Hidden-rowid table plus implicit autoindex (YCSB shape) |
| overflow-chain | 4096 | accepted | Overflow chain, 9 KB row beside an inline row |
| freelist-after-delete | 4096 | accepted | Freelist trunk and leaves after a bulk delete |
| post-vacuum | 4096 | accepted | Repacked file after VACUUM |
| auto-vacuum | 4096 | accepted | auto_vacuum=FULL, so the file carries pointer-map pages |
| real-values | 4096 | accepted | REAL storage class, read through ordering and a range predicate |
| blob-values | 4096 | accepted | BLOB storage class, read through equality and ordering |
| null-values | 4096 | accepted | NULL payloads and three-valued IS NULL |

## Forward-direction results, and the one declared exception

`scripts/run-forward-compat.sh` runs all eleven workload shapes in
`tests/sql/workloads`, twice per shape: once with SQLeanite as the writer, once
with C SQLite as the writer. C SQLite is then the *only* reader of both files, so
our result rendering is out of the comparison. Per shape it checks
`PRAGMA integrity_check`, `PRAGMA foreign_key_check`, C's view of the schema, and
C's row contents table by table.

Ten of eleven shapes are clean on every check. One has a declared, bounded
exception:

| shape | what C reports | why it is admitted |
|---|---|---|
| `08_bulk_delete` (empties an indexed table) | `Page N is never used`, 2 pages at the 200-row shape | Rows are exactly what C computes; the pages are allocated but unreferenced, not corrupt |

The cause is a design decision, not an accounting slip:
`CoreChunkPageDelta.updateState?_freedPageNumbers_eq_nil_of_indexed` makes an
indexed localized delta *allocation-preserving*, which is what lets a commit skip
a second allocation scan. Publishing the collapsed trees' pages to the freelist
needs the index trees' page sets inside the freed-set proof, which is proof work
rather than a one-line change.

It is admitted only because it is bounded and transient, and both are checked
rather than asserted:

- `run-forward-compat.sh` fails if any complaint is structural rather than an
  unreferenced page, if the count exceeds the shape's bound, or if row contents
  differ at all;
- `scripts/regress-page-reclaim.sh` pins that re-inserting reclaims the pages,
  that `integrity_check` returns to `ok`, and that five empty/refill cycles do
  **not** grow the file. An accumulating leak — the version that would matter —
  fails that script.

For the same program C SQLite ends at 5 pages where SQLeanite ends at 7 while the
table is empty. That gap closes on the next insert.

## Untested, and named so it is not mistaken for accepted

- files with more than one table carrying overflow *and* an index at a non-4096
  page size simultaneously (the cross of three features at once);
- files produced by SQLite versions older than the format-3 era, and encrypted
  or page-checksummed variants;
- `sqlite_stat1` and other internal tables written by `ANALYZE`;
- multi-column indexes, and indexes on expressions;
- `ATTACH`-ed multi-database files, and shared-cache access patterns.

These are untested rather than declared unsupported: no cell exercises them, so
nothing here says what happens. Do not report them as either direction.
